# 015. 위로 불러오기: sentinel + IntersectionObserver로 시작하고, useLayoutEffect에서 보정한다 (v5)

## 상황

과거 메시지를 목록 위에 붙이면, 그만큼 내용이 아래로 밀려 화면이 튄다. 그래서 `scrollTop`을 "새 높이 − 이전 높이"만큼 올려 보정해야 한다. 실무에서는 두 가지 방식이었다(LEARNING.md 8장).

- 시작 조건: `scrollTop <= 0`
- 보정 시점: 요청 promise가 끝난 뒤 `requestAnimationFrame`

이 보정 시점에는 두 가지 위험이 있다.

1. React가 새 메시지를 아직 DOM에 커밋하지 않았으면 이전 높이를 읽는다. 그러면 보정 값이 0이 된다.
2. 커밋과 보정 사이에 페인트가 한 번 끼면 한 프레임 튄 화면이 보인다.

## 검토한 대안

| 항목 | 대안                                        | 판단                                                                                                                         |
| ---- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 시작 | `scroll` 이벤트에서 `scrollTop <= 0`        | 정확히 0이 되어야만 시작한다. 관성 스크롤에서 놓치기 쉽다                                                                    |
|      | **맨 위 sentinel + `IntersectionObserver`** | 보이기만 하면 시작한다. 스크롤 이벤트 처리가 필요 없다                                                                       |
| 보정 | 요청 완료 → rAF (실무, v0~v4)               | 위의 두 위험                                                                                                                 |
|      | **`useLayoutEffect` (v5)**                  | DOM 커밋 후, 페인트 전에 실행된다. 새 높이를 정확히 읽고, 튀기 전에 보정한다                                                 |
|      | 브라우저 스크롤 앵커링(`overflow-anchor`)   | 크롬 계열에서는 자동으로 보정한다. 대신 Safari 지원과 동작 차이를 따로 확인해야 하고, 직접 하는 보정과 겹치면 두 번 보정된다 |
|      | `flex-direction: column-reverse`            | 위로 붙이는 것이 자연스러워진다. 대신 키보드 탐색 순서와 스크린리더 순서, 바닥 따라가기 로직이 모두 바뀐다                   |

## 결정

- 시작: 맨 위 sentinel + `IntersectionObserver` (모든 버전)
- 보정
  - v0~v4: 실무 방식(요청 완료 → rAF)
  - v5: 불러오기 직전에 `{ 높이, scrollTop, 첫 메시지 key }`를 기록하고, 첫 메시지 key가 바뀐 렌더(과거 페이지가 실제로 반영된 렌더)의 `useLayoutEffect`에서 보정한다.
    - 그 사이에 토큰 때문에 렌더가 와도 보정을 미리 쓰지 않는다.
- 바닥 따라가기는 마지막 메시지가 바뀌었을 때만 내린다. 위에 과거 페이지만 붙은 렌더에서는 내리지 않는다.
- 브라우저 스크롤 앵커링은 끈다(`overflow-anchor: none`). 보정 방식 두 가지를 비교하려면 브라우저가 대신 보정하면 안 되기 때문이다.

## 확인 방법

- E2E (v5): 맨 위로 올린 순간 보이던 첫 메시지의 위치가, 과거 페이지 반영 후 ±1px 이내다.
  - v5 보정을 지우면 이 테스트가 1,212px 차이로 실패한다.
  - 같은 테스트를 v4(rAF 방식)로 5번 돌리면 모두 통과했다. 스로틀링 없는 dev 서버에서는 rAF 전에 커밋이 끝났다.
- 측정: CPU 4배 느리게 한 조건의 위치 오차와 튄 프레임 (`docs/results.md`)

## 트레이드오프

- `overflow-anchor: none`이라서 이 앱은 브라우저의 자동 보정을 쓰지 않는다. 이미지가 늦게 로드되며 위쪽 높이가 바뀌는 경우도 직접 다뤄야 한다. 이 데모에는 이미지가 없다.
- iOS Safari의 관성 스크롤 중에 `scrollTop`을 바꾸면 스크롤이 멈추는 문제가 알려져 있다. 확인하지 않았다(`docs/manual-checklist.md`).

## 측정에서 확인한 것

[`docs/results.md`](../results.md)와 [`docs/results-raw.json`](../results-raw.json) 기준(버전마다 10회, CPU 4배 느리게, 과거 메시지 50개 로드)

| 보정 방식               | 실행 | 1프레임 이상 튐 | 보정 실패(위치 오차 > 1px)   |
| ----------------------- | ---- | --------------- | ---------------------------- |
| 요청 완료 → rAF (v0~v4) | 50회 | 50회            | 6회 (모두 3,195px, 11프레임) |
| `useLayoutEffect` (v5)  | 10회 | 0회             | 0회                          |

- rAF 방식은 보정이 맞은 실행에서도 모두 한 프레임은 밀린 위치로 그려진 뒤 보정됐다.
- 보정이 실패한 6회는 과거 메시지 50개의 높이만큼 그대로 밀렸다. [추정] rAF 콜백이 React 커밋보다 먼저 실행되어 이전 높이를 읽었다. 확인 방법: 보정 시점에 읽은 `scrollHeight`와 커밋 후 `scrollHeight`를 함께 기록한다.
- 결과표의 중앙값은 rAF 방식도 오차 0이라서 차이가 가려진다. 그래서 이 표처럼 실행별 횟수를 함께 본다.
