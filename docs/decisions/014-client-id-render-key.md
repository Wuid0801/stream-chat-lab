# 014. 렌더 key를 확정 전후 모두 clientId로 유지한다 (v4)

## 상황

v0~v3은 서버 메시지의 key로 서버 id를 쓴다. 낙관적 사용자 메시지와 스트리밍 말풍선은 clientId를 key로 쓰다가, 확정되는 순간 서버 id key의 행으로 바뀐다. React는 key가 다르면 다른 컴포넌트로 보므로, 같은 말풍선이 언마운트되고 다시 마운트된다.

- M3 측정에서 모든 버전의 리마운트가 턴마다 2회였다(사용자 메시지 1, 응답 1).
- 실무에서는 이 때문에 이미지가 다시 로드되고 애니메이션이 다시 재생됐다(LEARNING.md 7장).

## 검토한 대안

1. 서버 id를 key로 쓰고 리마운트를 감수한다 (v0~v3)
2. 확정 시 매칭된 clientId를 별도의 `renderKey` 필드로 넘겨받는다 — 서버가 clientId를 echo하지 않는 환경에서 쓰는 방법이다.
3. **서버가 echo한 clientId를 그대로 key로 쓴다**

## 결정

3번. `selectDisplayMessages(state, { stableKey: true })`는 서버 메시지의 key를 `clientId`로 만든다.

- 응답 메시지의 clientId는 `replyClientId(userClientId)`다. 스트리밍 말풍선의 key와 같다.
- 지난 대화(시드)도 서버가 clientId를 갖고 있으므로 key가 겹치지 않는다.
- 표시용 객체 캐시는 key 방식마다 따로 둔다. 같은 서버 메시지라도 key 방식에 따라 표시용 객체가 다르기 때문이다.

## 확인 방법

- 단위: 확정 전후의 key 목록이 같다(v4). 기본 방식에서는 다르다.
- E2E: 전송 직후 사용자 메시지의 DOM 노드를 잡아 두고 확정을 기다린다. v4에서는 같은 노드가 문서에 남아 있고, v3에서는 떨어져 나간다.
- 측정: 리마운트 칸 (`docs/results.md`)

## 트레이드오프

- 서버가 clientId를 echo한다는 계약에 기댄다. echo가 빠진 메시지가 섞이면 key가 비거나 겹칠 수 있다. 스키마가 `clientId`를 필수로 둔다.
- 서버 id로 행을 찾는 코드(예: 삭제, 수정)가 생기면 key와 id가 다르다는 점을 기억해야 한다.

## 측정에서 확인한 것

[`docs/results.md`](../results.md) 기준(버전마다 10회, CPU 4배 느리게)

- 리마운트: v0~v3은 턴마다 2회(10회 모두), v4·v5는 0회(10회 모두)
- 렌더 시간과 Long task는 v3과 v4가 비슷했다. 평균 렌더 0.5ms, Long task 중앙값 125.5ms / 134.5ms. 이 데모의 말풍선은 이미지나 애니메이션이 없어서, 리마운트 비용이 작은 조건이다.
