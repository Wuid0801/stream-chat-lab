# 012. EventSource와 fetch 어댑터를 같은 인터페이스로 두고, 차이는 숨기지 않는다

## 상황

M2는 네이티브 EventSource만 썼다. M4에서 `http-401`, `http-5xx`, `long-silence` 시나리오를 만들면서 EventSource로는 알 수 없는 것이 두 가지 드러났다.

1. **HTTP 상태 코드.** 스트림 요청이 401이든 503이든 `onerror` 하나로만 온다. 그래서 "재인증 안내"와 "재시도"를 나눌 수 없다.
2. **주석 하트비트.** 브라우저는 `: ping` 같은 주석 줄을 이벤트로 넘기지 않는다. 그래서 "일정 시간 아무것도 오지 않으면 끊긴 것으로 본다"는 타임아웃을 만들 수 없다.

## 검토한 대안

1. 하트비트를 주석 대신 `ping` 이벤트로 보낸다 — EventSource에서도 보이지만, 프로토콜에 "주석이면 충분한" 이벤트 종류가 하나 는다.
2. EventSource 실패 뒤에 상태 확인 요청을 따로 보낸다 — 요청이 늘고, 401과 5xx를 구분하려고 서버 API가 하나 더 필요하다.
3. **두 어댑터를 같은 인터페이스(`StreamTransport`)로 두고, 각자 알 수 있는 만큼만 알린다**

## 결정

3번. `?transport=eventsource|fetch`로 고른다(기본 eventsource).

|                | EventSource                     | fetch + M1 파서                        |
| -------------- | ------------------------------- | -------------------------------------- |
| 인증           | 쿼리의 1회용 토큰               | `Authorization` 헤더                   |
| 이어 받기 위치 | `?lastEventId=`                 | `Last-Event-ID` 헤더                   |
| HTTP 상태 코드 | 모름 → `stream-failed`          | 알림 → `unauthorized` / `server-error` |
| 하트비트       | 볼 수 없음 → idle 타임아웃 없음 | 바이트로 봄 → `idleTimeout`(기본 45초) |
| 취소           | `close()`                       | `AbortController`                      |

E2E는 시나리오 15개를 두 어댑터에서 모두 돌린다. 결과가 다른 시나리오(`http-401`, `http-5xx`, 하트비트 없는 `long-silence`)는 어댑터별 기대값을 따로 적는다.

## 트레이드오프

- EventSource에서는 401과 5xx가 같은 안내로 보인다. 재시도는 둘 다 된다.
- EventSource는 하트비트가 없을 때 죽은 연결을 늦게 알아챈다. 언제 알아채는지는 브라우저와 OS의 TCP 설정에 달려 있다. 측정하지 않았다.
- fetch 어댑터는 파서와 재연결을 직접 책임진다. 그 대신 M1 파서의 테스트(무작위 분할 500회 포함)가 그대로 안전망이 된다.
