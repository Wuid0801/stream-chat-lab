# 003. 보내기와 받기를 나누고, 스트림은 1회용 토큰으로 구독한다

## 상황

실무 구현은 메시지를 GET 쿼리 스트링에 실어, 요청 하나가 "보내기 + 받기"를 함께 했다(LEARNING.md 1장). 그래서 생긴 문제는 세 가지였다.

- 재연결이 곧 재전송이 되어 응답이 두 번 생성될 수 있다.
- 대화 내용이 URL에 남는다.
- 재시도와 이어 받기를 설계하기 어렵다.

## 검토한 대안

1. GET 하나로 보내기 + 받기 (실무 방식)
2. fetch 스트림 POST 하나 — 헤더와 body를 쓸 수 있다. 다만 브라우저 EventSource를 쓸 수 없어 두 전송 방식을 비교하려는 목표와 맞지 않는다.
3. **`POST /turns` → `GET /turns/:id/stream`**
   - 스트림 인증 방법으로 (a) 쿠키, (b) 쿼리의 데모 토큰, (c) 쿼리의 1회용 토큰을 검토했다.

## 결정

3번 + (c).

- `POST /turns`는 헤더로 인증하고 `{ turnId, streamToken }`을 돌려준다.
- `streamToken`은 60초 안에 한 번만 쓸 수 있다.
- fetch 어댑터는 같은 엔드포인트를 헤더로 인증한다.

## 트레이드오프

- URL에 토큰이 남는다. 짧은 만료와 1회 사용으로 노출 피해를 줄인다.
- (a) 쿠키는 이 데모에 CSRF와 도메인 설정을 끌어들인다.
- (b) 장기 토큰을 URL에 두면 로그 노출의 피해가 크다.
- EventSource 자동 재연결은 항상 실패한다. 의도한 동작이다(decisions/005).
- 요청이 하나 늘어난다(턴 생성 + 구독).
