# 011. 응답 생성과 연결을 분리하고, 끊기면 Last-Event-ID로 이어 받는다

## 상황

M2까지는 스트림 연결 콜백 안에서 토큰을 만들었다. 연결이 끊기면 클라이언트가 할 수 있는 일은 하나뿐이었다. `GET /turns/:id`로 서버 상태를 확인하고, 완료돼 있지 않으면 실패로 처리하는 것이다. 응답 도중 잠깐 끊긴 것만으로 턴 전체가 실패했다.

실무에서는 같은 상황에서 자동 재연결이 같은 요청을 다시 보내, 응답이 두 번 생성될 위험이 있었다(LEARNING.md 4장).

## 검토한 대안

1. 끊기면 턴을 다시 만든다 — 응답이 두 번 생성된다. 실무에서 피하려던 바로 그 문제다.
2. 끊기면 서버 상태만 확인한다 (M2 방식) — 생성이 끝나기 전에 끊기면 복구할 수 없다.
3. **생성을 연결과 분리하고 턴별 이벤트 버퍼를 둔다. 끊기면 마지막 이벤트 id부터 다시 구독한다**

## 결정

3번.

- **서버**
  - 첫 구독 때 생성기를 한 번 시작한다. 이벤트에 1부터 오르는 `id:`를 붙여 버퍼에 쌓는다.
  - 구독자는 `Last-Event-ID` 헤더 또는 `?lastEventId=` 쿼리 다음 이벤트부터 보낸 뒤, 새 이벤트를 기다린다.
  - 이어 받기용 토큰은 `POST /turns/:id/stream-token`으로 새로 발급한다.
- **클라이언트**
  - 토큰을 받는 중에 끊기면 0.5초 → 1초 → 2초를 기다리며 최대 3번 이어 받는다.
  - 이벤트를 받으면 시도 횟수를 다시 센다.
  - 3번 모두 실패하면 서버 상태를 확인한다(M2의 오탐 복구).
  - `done`을 받은 뒤의 끊김은 이어 받지 않는다. 생성은 이미 끝났기 때문이다.
- 이미 받은 `seq`의 토큰은 무시한다. 스트림 텍스트와 `final` 텍스트가 다르면 계약 위반을 경고한다.

## 확인 방법

E2E `drop-mid-stream`을 두 어댑터 모두에서 돌린다.

- `POST /turns`가 1번만 나간다.
- 두 번째 구독에 `lastEventId`가 실린다.
- 계약 위반 경고가 없다.

이어 받기를 끄고 같은 E2E를 돌리면 실패하는 것도 확인했다.

## 트레이드오프

- 서버가 턴마다 이벤트를 메모리에 보관한다. 목 서버는 지우지 않는다. 실제 서버라면 TTL이나 크기 제한이 필요하다.
- 이어 받는 동안(최대 3.5초 + 요청 시간) 화면은 마지막 토큰에서 멈춰 있다.
- EventSource의 자동 재연결 대신 직접 다시 연결한다. 새로 만든 EventSource는 `Last-Event-ID` 헤더를 넣을 수 없어서 쿼리로 보낸다.
