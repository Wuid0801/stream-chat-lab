# 002. SSE 파서: 줄바꿈 통일과 id / retry 의미

## 상황

fetch 스트림을 직접 파싱하면 청크 경계가 이벤트·줄·UTF-8 문자 경계와 맞지 않는다. SSE는 `\n`, `\r\n`, `\r`을 모두 줄바꿈으로 인정한다. 실무에서는 빈 줄 패턴(`\r\n\r\n|\n\n|\r\r`)을 나열해 잘랐는데, 줄바꿈이 섞이면(`\r\n\r`, `\n\r\n`, `\r\n\n`) 경계를 놓쳐 두 이벤트가 하나로 합쳐졌다(LEARNING.md 2장).

## 검토한 대안

1. 빈 줄 패턴 나열 — 줄바꿈 혼용에서 경계를 놓친다.
2. 문자 단위 상태 기계 — 정확하지만 코드가 길고, 이 저장소의 목적(문제와 해결을 보여 주기)에 비해 읽기 어렵다.
3. **줄바꿈을 먼저 `\n`으로 통일한 뒤 `\n\n`으로 자르기** — 단, 청크 끝의 `\r`은 다음 청크의 `\n`과 짝일 수 있으므로 통일하지 않고 남겨 둔다.

`id`와 `retry`를 출력에 어떻게 담을지도 정해야 했다.

- (a) 그 이벤트 블록 안에 있던 값만 담는다 — `retry: 3000`만 있는 블록처럼 data가 없는 블록의 값이 사라진다.
- (b) **표준처럼 연결 단위 상태로 유지한다** — `id`는 last event ID, `retry`는 마지막 유효 값.

## 결정

- 3번 방식. `end()`에서는 디코더에 남은 바이트와 남겨 둔 `\r`까지 포함해 한 번 더 처리하고, 빈 줄로 끝나지 않은 마지막 조각은 버린다.
- `id` / `retry`는 (b). 이어 받기(M4)에 필요한 값은 "마지막으로 받은 id"이기 때문이다.
- BOM은 `TextDecoder` 기본 동작(`ignoreBOM: false`)으로 제거한다. 바이트 단위로 쪼개진 BOM도 테스트로 확인했다.

## 트레이드오프

- 미완성 조각을 청크마다 다시 정규화하므로, 하나의 거대한 이벤트가 아주 많은 청크로 쪼개져 오면 비용이 청크 수에 비례해 늘어난다. 토큰 단위 이벤트는 작아서 문제가 되지 않는다고 판단했다(측정하지 않음).
- `retry`를 파싱만 하고 재연결 지연에 쓰지는 않는다. 재연결 정책은 전송 어댑터(M4)가 정한다.
