# 009. 렌더 비교 버전은 플래그 세 개로 만들고, 한 번에 기법 하나씩 더한다

## 상황

실무에서는 토큰마다 dispatch하고, 스트리밍 말풍선을 매번 마크다운으로 다시 파싱했다. 비용을 측정한 적은 없었다(LEARNING.md 7장). 기법을 한꺼번에 넣으면 어느 기법이 얼마나 효과가 있는지 알 수 없다.

## 검토한 대안

1. 버전마다 컴포넌트를 따로 만든다 (`ChatViewV0` …) — 코드가 중복되고, 버전 사이에 의도하지 않은 차이가 생기기 쉽다.
2. **같은 컴포넌트에 플래그 세 개(`memoPast`, `rafBatch`, `plainWhileStreaming`)를 두고, `?v=`가 플래그 조합을 고른다**

## 결정

2번. v0 → v3로 갈 때마다 플래그를 하나씩 켠다. 기본값(`?v` 없음)은 최신 버전이다.

v1(memo)에는 다음 두 가지를 함께 넣었다. 이것이 없으면 `memo`를 붙여도 아무것도 막지 못한다.

- `selectDisplayMessages`가 바뀌지 않은 메시지의 표시용 객체를 그대로 돌려준다(WeakMap 캐시). 원래는 토큰 하나에 모든 메시지의 객체를 새로 만들었다.
- 행에 넘기는 콜백(`onRetry`, `onCopy`)을 `useCallback`으로 고정한다.

rAF 배칭(v2)은 `createTokenBatcher`로 분리해 단위 테스트한다.

- `final`이나 실패를 반영하기 전에 즉시 flush한다. 백그라운드 탭에서는 rAF가 멈추기 때문이다.
- 언마운트 때 예약된 프레임을 취소한다.

## 트레이드오프

- 기본값이 v3라서 기존 E2E는 v3에서 돈다. 다른 버전은 `variants.spec.ts`가 완료까지 동작하는지만 확인한다.
- v1에서 콜백 고정과 객체 유지를 memo와 함께 묶었다. 그래서 "memo만"의 효과를 따로 측정하지는 않는다.
- 플래그 분기가 렌더 경로에 남는다. 측정용 저장소라 감수한다.

## 측정에서 확인한 것

값은 [`docs/results.md`](../results.md)의 중앙값이다(버전마다 10회, CPU 4배 느리게).

- **v0 → v1 (memo)이 가장 크다.**
  - 평균 렌더: 53.1ms → 4.1ms
  - Long task 총합: 37,608.5ms → 200ms
  - INP: 156ms → 44ms
  - v0은 스트리밍 37.5초 동안 Long task가 거의 끊이지 않았다.
- **v2 (rAF 배칭)는 이 조건에서 커밋 수를 줄이지 못했다.**
  - 커밋 수: 1,498 → 1,492
  - 40 tokens/s면 토큰 간격이 25ms다. 한 프레임(약 16.7ms) 안에 토큰이 둘 이상 모이는 일이 드물다. [추정] 토큰이 더 빠르게 오거나 프록시가 몰아서 보내는 조건(M4 `proxy-buffering`)에서 다시 잰다.
- **v0의 커밋 수(712)가 토큰 수(1,500)보다 적다.** [추정] 메인 스레드가 막혀 있는 동안 쌓인 dispatch를 React가 한 번에 처리했다. 확인 방법: 커밋마다 반영된 토큰 수를 기록한다.
- **v3 (평문)은 평균 렌더를 4.2ms → 0.5ms로 줄였다.**
  - 대신 최대 렌더는 80.4ms → 124.9ms로 늘었다.
  - [추정] `final`에서 1,500토큰을 한 번에 마크다운으로 파싱하기 때문이다. 확인 방법: 최대값이 나온 커밋이 마지막 커밋인지 기록한다.
- **리마운트는 모든 버전에서 2다.** key가 서버 id라서, 확정될 때 사용자 메시지와 응답이 한 번씩 다시 마운트된다. M4의 v4(key = clientId)와 비교할 기준값이다.

## 이후 추가된 버전 (M4)

- v4: 렌더 key를 clientId로 유지 — [014](014-client-id-render-key.md)
- v5: 위로 불러오기 보정을 `useLayoutEffect`로 — [015](015-scroll-correction-timing.md)

M4의 재측정(v0~v5, 커밋 `c70db29`)에서 v0~v3의 값은 M3와 같은 경향이었다. 다만 M4 측정은 조건이 하나 다르다. 서버에 메시지 400개를 채우고, 턴 뒤에 과거 페이지를 불러온다. 그래서 M3 표와 칸별로 비교하지 않는다.

## proxy-buffering 조건에서 rAF 배칭 다시 재기 (M4-3)

M3에서 rAF 배칭(v2)이 커밋 수를 줄이지 못했다. 그래서 토큰이 몰려 오는 조건에서 다시 쟀다. 결과는 [`docs/results-proxy-buffering.md`](../results-proxy-buffering.md)에 있다(v1·v2 × 10회, 커밋 `ced0ff9`). 프록시가 2초씩 모아 보내는 조건이다.

- 커밋 수/턴: v1 25.5, v2 26 (중앙값). 토큰 1,500개에 커밋이 26번 안팎이다.
- 평균 렌더: v1 14.3ms, v2 13.9ms. Long task 총합: v1 156ms, v2 145ms. 차이가 p90 범위 안이다.
- **rAF 배칭을 하지 않은 v1도 이미 몰려 온 이벤트를 몇 번의 렌더로 묶었다.** [추정] 한 번에 도착한 이벤트들의 dispatch가 React의 렌더 작업보다 먼저 큐에 쌓여, 한 렌더에 함께 반영됐다. 확인 방법: 커밋마다 반영된 토큰 수를 기록한다.

정리하면, 이 저장소의 두 조건(40 tokens/s로 고르게 도착, 2초씩 몰려 도착)에서 rAF 배칭의 효과는 측정되지 않았다. 효과가 날 수 있는 조건은 토큰이 서로 다른 task로, 프레임(약 16.7ms)보다 짧은 간격으로 도착하는 경우다. 그 조건은 재지 않았다. 기법은 남겨 두되, README에는 효과가 측정되지 않았다고 적는다.
